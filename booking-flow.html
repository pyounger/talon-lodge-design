Talon Lodge & Spa · Scheduling architecture

How a booking is made — and how two groups can't grab the same guide

An activity or massage request enters through one of three doors, becomes a hold that reserves real capacity on a real date, and is confirmed into an assignment. The whole reserve step is a single locked transaction, so the last seat can only be sold once.

01

Three ways a booking starts

At reservation, from the guest portal after booking, or by an admin — all funnel through the same capacity gate.

Path A — Booking flow

On the Activities step, while building the reservation, the guest picks activities for their trip days. Fits the rules → an instant hold under their group name.

Path B — Guest Portaltwo-way

After booking, the portal's Activity and Massage modules let the guest request more — and watch each one move from Requested to Approved. Some activities are portal-only (set per activity in Activity setup), so they appear here and never at reservation.

Path C — Admin direct-book

The admin schedules straight onto the calendar and can do what guests can't: mixed group on a guide, override the lead-first pick, resolve a full day.

02

The life of a booking

Every booking is a row that moves through states — and only two of them hold capacity.

The Guest Portal is where the guest lives inside this state machine after booking. Its Activity and Massage modules submit new requests and show each one's status — Requested while it's a pending hold, Approved once the admin confirms it, or declined with alternatives offered. The guest never sees the resource math or other groups — only their own items and exactly where each one stands.

⏱ 24-hour review SLA. Every pending request — whether it came from the portal or the reservation flow — notifies the admin the instant it lands and starts a 24-hour review clock. The admin review queue shows time remaining per request; anything nearing or past 24h escalates (flag + reminder) so no guest is left waiting on an answer. Approve → Assignment; decline → released with alternatives offered back in the portal.
03

The rule the whole system defends

One equation, checked inside a lock. Everything else is plumbing around it.

Availability is never stored — it's derived for a resource on a date, every time it's asked:

available(resource, date) = capacity(resource) − Σ holds(resource, date) − Σ assignments(resource, date)
a booking is allowed ⟺ requested ≤ available AND rules pass (during-stay · party ≤ guide cap · not mixed-group · saltwater ≥ 4 · has delivery boat)

Because a hold counts the instant it's created — whether from the booking flow or a portal request — the seconds between selecting an activity and confirming can't be used by anyone else to oversell it. The invariant to protect: for every (resource, date), holds + assignments never exceed capacity.

04

Two requests, one seat — who wins

The concurrency case: two groups book the last spot on Ted for the same day at the same instant — one from the portal, one from the booking flow.

That lock is the primary guarantee, but it's backed by layers so a race can't slip through another way:

  • Atomic check-and-reserve (the lock above)The availability re-check and the insert happen in one transaction that locks the (resource, date) row. Concurrent bookers serialize; the loser re-reads the updated count and is rejected. No “read-then-write” gap.
  • Database constraints as a backstopA unique index on (guide_id, date, activity) makes a double guide-day physically impossible even if app logic is bypassed; the same for (saltwater_boat, date) and one hold per delivery boat per day. The DB refuses the second write.
  • The hold reserves during checkout & approvalBecause a hold counts against availability the instant it's created, the window between “guest requests” and “admin approves” can't be used to oversell. Holds persist until an admin releases them — no silent timeout drops a seat back into the pool.
  • Idempotency key on submitA double-click or a network retry — common on the portal — carries the same key, so the reserve is applied at most once. One tap doesn't become two holds.
  • Edge cases escalate, never auto-bookParty > 6, mixed groups on a guide, and over-capacity days become requests the admin resolves by hand — they never quietly consume a resource. Archiving a guide (Team admin) surfaces their live holds for reassignment instead of vanishing them.
🛟 Prototype vs production. Today's demo stores holds in the browser (talon_bookings_v1) — a single tab, so there's no real race. The guarantee described here is what the Laravel/Aurora backend enforces: the reserve is a DB transaction with SELECT … FOR UPDATE plus the unique constraints, so the check and the write are one indivisible step. The demo already models the shape — holds by real date, shared across groups — so wiring the booking flow and the guest portal to it is a swap of the storage layer, not the logic.
