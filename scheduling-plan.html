Talon Lodge & Spa · Scheduling Plan

Activity & massage scheduling

This is the hardest part of the platform, and it's worth naming why: availability isn't a fact we store — it's derived every time from who's working, what each person can run, and how many seats are left on a given day. A guest asks "can I get a massage Wednesday, or fish by float plane Thursday?" and the answer depends on therapists, guides, and boats — finite resources with hard caps — not on the activity itself.

So the plan below models the resources first, states the capacity rule for each activity type, then derives a live availability calendar that feeds two booking paths: a guest request that places a hold, and an admin who confirms and assigns the actual guide or therapist.

03 How availability is derived

The calendar is computed, never stored. Resources set capacity → holds and confirmed assignments consume it → what's left is what a guest sees.

04 Two ways to book

Both end in the same place — a confirmed assignment on the calendar — but they start differently.

A
Guest requests through the booking engine
The guest picks an available day; the system places a hold (pending) so the seat can't be double-booked. Nothing is confirmed yet — it needs staff sign-off. Creates a reservation_request line + a pending assignment.
→
Admin confirms & assigns the specific guide / therapist
In the control panel the admin sees the hold, picks the resource (Ted before Holden; a therapist with an open slot), and confirms. The hold becomes a firm assignment; if nothing's available the admin can decline or offer another day.
B
Admin books directly in the control panel
Staff can add an activity or massage to a reservation and assign the guide/therapist in one step — no guest request needed (walk-ups, phone bookings, comps).

05 Build plan

Model the resources first, then the engine, then the two surfaces that read it.

  1. Team & capability model builds on existing schema
    Add guides & therapists as assets; record what each can run and the lead/second order via asset_links; store per-resource caps (guide = 3, therapist = 2 sessions, boat = 1). A "Team" admin to add/edit them — same Export→seed pipeline as Rooms/Activities.
  2. Availability engine
    The core function: for a day + activity + party, return available / held / full by walking capable resources, subtracting existing holds & assignments, and applying the party rules (min-4 saltwater, 3-per-guide, >6 request-only, mixed-group).
  3. Guest activity calendar + request → hold
    In the booking flow, each activity opens a calendar scoped to the guest's stay showing only truly bookable days. Selecting one places a hold and tells the guest it's pending confirmation.
  4. Admin control panel — confirm, assign, direct-book
    A day/resource board: pending holds to confirm with a suggested assignment (lead-first), plus direct booking. Everything writes to the one assignments table so the calendar stays truthful for the next guest.
  5. Overbooking guards & hold expiry
    Atomic seat checks so two simultaneous requests can't take the last slot, and an auto-release so stale holds free up.

06 Decisions

Three are locked; two small ones remain before Phase 3.

✓ Locked · Guide capacity

3 guests max per guide, one activity per day. A guide runs a single activity each day — the tighter, cleaner calendar.

✓ Locked · Saltwater crew

Separate captain & boat crew. Independent of Ted & Holden, so the Additional Saltwater Day never competes with the guided-activity calendar.

✓ Locked · Day Spa staffing

Staffed separately. A Day Spa booking doesn't reduce the 4 daily massage slots (4:30 & 5:30 stay intact).

Open · Mixed groups on a guide

Can a guide's 3 seats be filled by two different small groups (e.g. 2 + 1)? The rule says "more than 3 must be same group," which implies ≤3 can mix — confirm that's intended.

Open · Hold expiry & the "request only" path

How long should a guest hold last before auto-releasing? And for parties over 6 (request-only), should the booking engine collect the request and route it straight to the admin queue with no availability shown?

Recommended first step: build Phase 1 + 2 — the Team admin and the availability engine — with a small demo calendar so you can watch a day fill up (Ted → Holden → full) and see Kayak/Whale bottleneck on Ted. Everything after that reads the same engine.
