The big picture

The system reads left‑to‑right as one guest's journey

The platform is organized as six phases of a single guest lifecycle — set up the inventory, sell it, prepare the guest, run the stay, follow up, and merge the history. Each phase stands on a shared layer of platform services (billing, comms, availability, storage, auth, multi-site tenancy), and each phase writes back to one People & Trip record at the center. The capability map below is the whole system on one page.

Capability map. Columns are the five stay phases in order; every card is a module. Below them, the golden record everything reads and writes; below that, the shared platform services every module depends on.

Four brands run on the one platform as tenants — Talon Lodge, Bluff House, Alaska Luxury Lodge, and Magnus Adventures — and each embeds a live availability widget into its own public website. A guest booking on any affiliated site can see and book across the affiliation.

The organizing principle is stated bluntly in the design docs: the master person record is "the most critical element of the platform." Everything funnels to the individual; the group is only how people book.

The data model

Everything hangs off one person

A human enters through one of several intake channels, is resolved to a single person master record, and then accumulates groups, trips, per-trip profiles, and day-by-day asset assignments over years of visits. History only accumulates — it is never overwritten. This is the schema spine.

The schema spine. Intake → matching → person (one master record) → group_persons / group → trip → trip_profiles (a snapshot per person, copied forward each visit) → assignments (person + asset + date) → assets. A booking agent's shared inbox lives on the group and is never merged into a person.

The design is deliberately hybrid: a strict relational spine (person, group, trip, assignments, matching, money) plus governed JSON bags — assets.properties, trip_profiles.details, assignments.details — so new offerings and custom fields need no migration. Rooms, boats, guides, massage, activities and breakfast are all just assets; anything scheduled is an assignment. Every table carries a public ulid, an active soft-delete flag (no hard deletes, ever), and audit columns.

Phase 5Follow upPost‑stay · automated

After departure, post-stay communications send a native satisfaction survey (replacing SurveyMonkey). The score is appended to each guest's record and feeds their lifetime rollups — latest_survey_score, avg_survey_score — closing the loop back to the person.

Why it matters

Because the survey score attaches to the person, not the trip alone, the next time that guest inquires — years later, in a different group — the office already sees their satisfaction history, past boats, guides and preferences. The follow-up phase is what makes the next first phase smarter.

How data flows

One record, handed from module to module

The screens above aren't independent apps — they pass a single thread of data down the line. Three intake channels feed one matching engine; from the resolved person, the booking opens a group and trip; the portal and approvals fill the schedule; operations run off the assignments; and the survey rolls back onto the person.

Then it closes the loop: the post-stay survey writes a survey_score back onto the person, updating lifetime rollups — so the next inquiry from that guest starts already knowing them. In the prototype every tool shares one browser-storage dataset on a single origin; in production that is the one Aurora database, and the golden person record is what every module reads and writes.

Cross-module dependencies are real

Because it's one dataset, changes ripple: archive a boat or guide in Team and Scheduling capacity drops that instant. A person who is both captain and guide is pulled from the guide pool on any day their boat is fishing. Over-capacity is flagged, not blocked — built for large groups rotating boats daily. These behaviors are defined in the prototypes and are the behavioral spec for the build.

Master record & migration

The individual is the record

Exactly one master person per human. A person is never re-created; every arrival is matched against who's already known. This is the engine that lets the platform replace three legacy systems — reservations, the profile/activity system, and SurveyMonkey — and merge them into one history. It was validated against four real 2026 exports totaling 2,706 rows.

All intake — a website form, a booking, a lead-submitted guest list — produces a candidate that runs through the same resolveGuest() engine. None creates a person directly; the engine either links to an existing master record or creates a new one.

  • Tier 1 — exact email → auto-link. Guardrail: if one email maps to two or more different people, it's a shared or agent inbox — do not merge. Store it on the group's booking-agent fields and flag for review.
  • Tier 2 — exact phone + nickname-equivalent name → auto-link. The same phone with different names is a household, not one person — don't merge.
  • Tier 3 — name only → never auto-merge. One contactful match auto-attaches; multiple go to a review queue; none stays unlinked, to be linked later. Ambiguous nicknames (Pat, Chris, Sam…) are never auto-canonicalized.
  • Never infer identity from a shared email domain, and never dedupe trips — multiple bookings by one person are simply multiple trips.

Merge is reversible, and IDs are forever

A merge combines two existing people under a survivor (chosen by most history → earliest first-seen → most complete → lower id). The survivor keeps its id and ulid for life; the loser's ulid becomes a redirect so old magic-links and invoices still resolve. Every merge stores full before-snapshots and the exact records it re-pointed, so it can be undone precisely — newest-first. Records that started pointing at the survivor after the merge stay put.

Run it many times into staging, once into production

Per the plan: build the importer as an idempotent, repeatable migration — re-runnable into staging until the mapping is right (upserts keyed on legacy source IDs, wrapped in transactions), which doubles as the seed for dev and staging databases. Then run it once into production. The recommendation is to build it as a Laravel Artisan command inside the API so it targets the real schema and can't drift; the matching / merge rules stay here in the design repo as the master spec.

One note for the build team

An older SERVER_SETUP.md in the design repo describes a superseded Postgres + Node + React stack — the project pivoted to MySQL + Laravel + Angular. Treat that file as infra/ops reference only (private-subnet DB, presigned S3, SES magic-link, snapshot-before-migrate all still apply); the current app stack is the one above. And on the Daxa theme: pin exact versions / commit a lockfile and install with --legacy-peer-deps, or ng serve throws ~90 type errors that aren't your code.
