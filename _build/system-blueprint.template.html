System Blueprint · Guest Lifecycle

One guest, start to finish.

How the whole platform fits together — from the master record a guest is born into, through every room, boat, activity, meal and massage, to the survey score and notes that travel with them into the next season.

Draft for review For the Talon team & Stella dev v1 · September 2026 23 stages · 46 screens

This document walks the entire guest lifecycle in the order it actually happens, one stage at a time. Every stage shows the business rules that govern it, whether the screen is admin-facing or guest-facing, how it maps to the database, and a screenshot of the working prototype so there's no guessing what "done" looks like.

It has two audiences. For the Talon team, it's the place to confirm the rules match how the lodge really runs — mark anything that's wrong and we'll change it. For Stella's developers, it's the guide to what each screen does and the schema it writes to. Everything pictured is a real, clickable prototype; the closing section is honest about what's fully built versus what still needs the backend.

The one idea everything else hangs on

Everything funnels to the individual guest. The group is only how people book — every assignment, order, catch, score and note attaches to the one person, and accumulates across every visit, forever.

Phase A

Foundation & setup

Before a single booking, two things must exist: one clean record per human being, and every resource the lodge offers — rooms, activities, crew, menus — entered once as a catalog. The whole platform is built on these two.

01

The person record — the spine

People arrive through three different doors, but the system keeps exactly one master record per human. Every arrival is matched against who's already known; certain matches fold in, new people get a fresh record, and uncertain cases wait for a human. From then on, a person's whole history lives on that single record.

Admin · back office

    Business rules

  • One master Person per human — history only ever accumulates, it is never overwritten.
  • Three intake doors all run the same matching engine: the website contact form, a reservation booking, and the guest list.
  • Tiered matching: Tier 1 — exact email → auto-link · Tier 2 — phone + nickname-equivalent name (Bob = Robert) → auto-link · Tier 3 — name only, no contact → waits in a review queue for a human.
  • A role (lead / member) lives on a person's membership in a group, not on the person — so a past guest can become a lead later and the record shows both.
  • A booking agent or shared inbox is stored on the group, and is never merged into a guest's person record.
  • Nothing is ever hard-deleted (soft-delete only), and every merge is reversible — the losing and surviving records are snapshotted so a merge can be undone precisely.

Maps to schema

Intake rows (inquiries, leads, reservation_requests, guest_list_entries) each keep their raw data plus a person_id. The matcher resolves to one persons row with child person_emails · person_phones · person_name_aliases. Merges are logged in merge_history (undo-safe); unresolved Tier-3 cases sit in merge_review_queue.

02

Resource & catalog setup

Rooms, activities, boats, guides, breakfast and beverages are all the same kind of thing: an asset with a type and a bag of properties. Each one is entered once in its own admin editor and exported to seed production — that catalog is what every later screen draws from. It's also the schema trick that lets the lodge add a new offering without a database migration.

Admin · setup

    Business rules

  • Every offering is an asset of a type — Room, Activity, Boat, Guide, Captain, Deckhand, Breakfast, Beverage — with a JSON properties bag (description, photos, capacity, price…).
  • Guides link to activities; captains and deckhands crew the boats — those relationships are stored as asset-to-asset links.
  • Breakfast is offered as 4–5 options per morning; beverages are sold by the 6-pack and stocked onto boats.
  • A package bundles assets (rooms + activities) as package assets, which is what drives availability and pricing later.
  • New field or new asset type? It's defined as data, so it appears everywhere without a code change.

Maps to schema

One assets table (asset_type + properties JSON) covers every offering; crew and guides attach via asset_links. Packages point at assets through package_assets. All type-specific fields are governed by field_definitions (the meta-schema) — no migration to add a room amenity or a new tour.

Each resource type has its own editor. Enter it once, export the catalog to seed production, and it's live everywhere. Below: rooms, activities, and the team & crew that create activity availability — plus menus, beverages, the massage menu, fish types and vendors, which follow the same pattern.

Phase B

Packages & availability

With resources catalogued, the lodge builds its sellable product: packages priced off those assets, and a season calendar that shows exactly what's open on every departure.

03

Package set-up & pricing

A package is one departure — its series, category, what's included and excluded, its rooms and activities, deposit and pricing. The title, price range and date range are computed, never stored, and dynamic pricing is applied to the base rate automatically. The booking engine reads all of this live.

Admin · setup

    Business rules

  • Each package is one departure — series, category, nights, adventure days, Includes / Does-Not-Include lists.
  • Rooms & activities are read live from their catalogs; a package's title, price range and date range are computed, not typed.
  • Publishing is guarded — a package can't go live oversold or mis-configured.
  • Revenue management applies dynamic pricing to the base package rate only (not activities or spa): a last-minute discount within a set window of arrival while rooms remain, a price floor, and high-demand step-ups. The confirmed rule is 10% within 15 days of departure.
  • The deposit never changes with dynamic pricing.

Maps to schema

A packages row points at rooms and activities through package_assets. Computed fields (title, price range, dates) are derived at read time from the assets and the season, never persisted. Revenue-management parameters live on the package.

04

The season availability calendar

Every 4-night departure × every room, for the whole season, on one grid. Availability is the rooms selected in the package times their occupancy. Each cell's colour is its booking state, holds carry a countdown, and clicking a booking opens its full reservation detail.

Admin · reservations

    Business rules

  • The grid is every departure × every room; availability = the package's selected rooms × their minimum occupancy.
  • Each cell carries a booking state — Available · Confirmed (deposit in) · Reserved (deposit due) · Held (guest deciding) · Prospect (to book).
  • A Held cell shows a countdown (e.g. "3d left") so the desk knows when a soft hold expires.
  • Special weeks (Winemaker, Chef) are flagged on their departures.
  • Clicking a booking opens the reservation detail — lead, status, confirmation code, party, payment history and accommodations; open cells add a new booking.
  • The whole season exports to Google Sheets for offline review.

Maps to schema

The grid is derived: trips and their room assignments placed against each package's package_assets and dates. Cell state comes from the trip's booking status and deposit; the hold countdown from the hold's timestamp.

Phase C

The reservation

How a booking actually gets made — the guest's step-by-step reservation, the capacity gate that makes it safe, and who pays for what.

05

The availability widget & reservation

This is the public availability widget on the lodge websites, and the reservation it flows into. The guest enters their dates and party size; every package that fits renders as a result; they open a package to see the rooms available, pick a room, and move through a guided nine-step flow — season & party → arrival date → rooms → your details → guest list → activities → review → deposit → confirm. A date is only offered when the open rooms can seat the party exactly; submitting creates the booking and resolves the booker to a person.

Guest · public site & reserveAdmin · can book too

    Business rules

  • Party size is in doubles (double occupancy); a date appears only when available rooms seat the party exactly — no more, no less.
  • The guest picks rooms until the party is covered exactly, then enters lead details.
  • The guest list can be filled now or later; each guest is set to send a portal invite or managed by the lead, and returning guests are matched live (Past-Guest badge).
  • Activities are optional add-ons — pick who joins and which day; fees are paid at checkout, not in the deposit.
  • Review shows the whole order and the payment schedule: deposit due now, balance due 120 days before arrival.

Maps to schema

Submitting creates a reservation_request that resolves into a group + trip, with group_persons (lead + members) and an assignment per chosen activity. Rooms and activities are the same assets read by the calendar; each guest resolves to one person (Stage 1).

06

Booking capacity & holds

Behind every activity and spa booking is one capacity gate. A request enters through one of three doors, becomes a hold that reserves real capacity on a real date, and is confirmed into an assignment. The whole reserve step is a single locked transaction, so the last seat can only be sold once.

Admin · architecture

    Business rules

  • Three doors — the booking flow, the guest portal, and an admin booking directly — all funnel through the same capacity gate.
  • The reserve step is a single locked transaction (lock · re-check · insert) so a seat is sold exactly once.
  • The life of a booking: Request → Hold → Assignment → Released — and only Hold and Assignment consume capacity.
  • A guest booking that fits the rules skips Request and lands directly on a Hold; party > 6, mixed-group, or over-capacity waits as a Request for the admin.
  • Holds don't auto-expire — they hold until an admin releases them; releasing returns the seats.

Maps to schema

Every booking is an assignment row moving through states; capacity is checked against the asset's limit at reserve time inside one transaction. The guest portal reads each item's status back (Requested → Approved / Declined).

07

Who pays — payment responsibility

At check-in — in the portal or at the desk — the group lead sets who pays for each guest's add-ons. Every activity, spa and alcohol charge routes to the chosen payer's folio at checkout, and each guest confirms what they're responsible for and how their fish gets home.

Admin · check-inGuest · confirms

    Business rules

  • Per guest, per charge type — activities, spa & massage, alcohol, fish processing — the payer is Self, the group lead, or another guest.
  • Shortcuts set a whole group at once: lead covers everything, or everyone pays own.
  • The guest sees their folio and confirms responsibility; the choice saves to each guest's record automatically.
  • Fish handling is chosen here too — carry it on the plane, or ship via FedEx.
  • No card number is ever stored — only a payment-method reference.

Maps to schema

Charge routing is stored per guest per charge type and applied to the folio at checkout; fish handling lands in fish_processing. Payment uses a payment_method_id reference — never a raw card number.

Phase D

Pre-arrival

Once booked, the party is gathered and each guest gets a portal to ready themselves — profile, dietary needs, flights and fishing licence — before they arrive.

08

The guest list

Once the booking is made, the lead's guest list is gathered — each traveller matched to the master database (Stage 1) and given their own portal invite. From that moment the lodge sees, per guest, exactly how ready they are for the trip: profile, address, sizing, emergency contact, health, airfare and licence.

Admin · rosterGuest · guest list

    Business rules

  • The booker becomes the group lead; a scheduled post-confirmation message requests the full guest list.
  • Each named traveller is matched to the master record (Stage 1) and linked to the group as a member, with their own portal invite.
  • Availability for a package = the rooms selected × their max occupancy; publishing is guarded so a package can't go live oversold.
  • A repeat-guest badge (R2, R3, R4…) surfaces returning guests at a glance, clickable through to their prior years.
  • Pre-trip readiness is tracked across seven dimensions — profile, address, sizing, emergency contact, health, airfare, fishing licence — so the team can chase exactly what's missing.

Maps to schema

A group is created with the lead on group_persons.role = lead; each guest becomes a member row. The booking is the trip (Group ↔ Trip is 1:1). Readiness is computed from each guest's trip_profiles completeness. Returning-guest counts come straight off the person's history across all trips.

09

The guest portal & profile

Between booking and arrival, the guest does their own preparation in a portal built for them — not the admin app. They complete a profile for this trip: personal details, dietary needs, emergency contact, flights, and their fishing licence. Anything they request is reviewed by the lodge within 24 hours.

Guest · self-serviceAdmin · reviews requests

    Business rules

  • The profile exists per trip and is copied forward from the guest's last visit — people change (boot size, diet, medical), so each trip snapshots its own, preserving history.
  • The guest captures dietary needs, allergies, emergency contact, flights in & out, and uploads their Alaska fishing licence.
  • Every activity or spa request the guest makes is reviewed within 24 hours before it's confirmed (Stage 6).
  • The portal is deliberately its own experience — no admin sidebar, luxury tone, real photography, no emoji.

Maps to schema

Writes a trip_profiles row (structured core fields + a details JSON governed by field_definitions), versioned and copied from the prior trip. The licence and photos become stay_media. Requests are written as pending assignments awaiting approval.

Phase E

Assignment

With the party known and the offerings set, the lodge places each individual guest — into a room, onto activities and the spa, onto the scheduling board, and onto a boat. Every placement is per person, and every placement flows into the daily run sheet.

10

Rooms

The reservation assigns the room(s) to the group; here the team places each individual guest into one of them. Over-capacity is accepted and flagged, never blocked — the lodge always knows better than the software. Every placement attaches to the guest, so it flows straight to the rooming list and the daily report.

Admin · lodging

    Business rules

  • Each individual guest is placed into a specific room — not just the group into a building.
  • Over-capacity is accepted and flagged, never blocked.
  • Staff can move anyone to any room lodge-wide from one board (24 guests / 24 beds when the lodge is full).
  • The assignment attaches to the guest, so it appears on the rooming list and the daily run sheet automatically.

Maps to schema

A per-person assignment of a Room asset to the guest for the trip. The room-level occupancy view is derived; the source of truth is one row per guest.

11

Activities & spa

Every activity and spa request — whether it came from the reservation or from the guest's own portal — lands in one approval queue on a 24-hour clock. Approving confirms it and the guest sees it as scheduled. Massage is booked per person, with a therapist, treatment and time for each appointment.

Admin · concierge

    Business rules

  • Requests from both the reservation flow and the guest portal land in a single queue, each on a 24-hour review clock.
  • Approving sets the request to confirmed; the guest immediately sees it as "scheduled" in their portal.
  • Massage is per person — each appointment carries its own guest, therapist, treatment and time.
  • Activities carry a guide (or pilot + vendor for fly-outs) and cap party size; the specific guide and boat are set on the scheduling calendar.

Maps to schema

Each request is an assignment (person + asset + trip + date) with a status; approval flips it to confirmed. Massage detail — therapist, treatment, time — lives in the assignment's details JSON, so the daily report and portal both read it. The SLA clock is tracked server-side.

12

Scheduling & the resource board

The activities calendar. Pick a package — its real arrival→departure dates become the grid — choose a group, then tick the individual guests on each activity. Bookings save against the actual date, so groups the same week compete for the same guides; the engine assigns the lead guide first. A resource board shows what every guide, therapist and boat holds, by date.

Admin · scheduling

    Business rules

  • The package's real dates become the calendar; stay days are bookable, arrival & departure are travel days.
  • Every activity is booked to the named individuals, not just the group — it attaches to the person.
  • Bookings save against the actual date and are shared across every group that week, so they compete for the same guides.
  • A guide holds one activity per day for up to its guest cap; the lead guide is assigned first, and lead-only activities (e.g. Kayak, Whale Watching) go dark once the lead is taken — the tightest bottleneck.
  • A booked adventure pulls that guest off the boat for the day; boats seated in Boat Assignments show on this master calendar.
  • The resource board shows each guide, therapist and boat's holds per date, for the selected package.

Maps to schema

Reads the trip's assignments against the team assets and their asset_links (capabilities, crew). Per-date resource availability is computed from what each guide/therapist/boat already holds; the lead-first rule and the one-activity-per-day cap are enforced at booking time.

13

Boats

Guests are seated on boats for their sportfishing — pick the day, then a group, then a boat. Each boat seats up to its set capacity, groups can share, and a guest keeps a "home boat" for the trip that can be switched for any single day. The key rule: on a day a guest has an adventure booked, that activity wins and they come off the boat.

Admin · dock

    Business rules

  • Seat guests by day → group → boat; each boat seats up to its set capacity (6, 4 or 2, from the crew setup).
  • Groups can share a boat, and if a group doesn't fully fit you choose who goes on it and place the rest elsewhere.
  • A guest has a home boat for the trip; a per-day switch overrides it for one day only.
  • Activity-priority rule: any day a guest has a scheduled adventure, that activity takes priority and they drop off the boat for the day.

Maps to schema

Boat seating is a per-person assignment of a Boat asset, keyed by trip and date (home seating with per-day overrides). Captain and deckhand come from the boat's asset_links. The activity-priority rule is resolved at read time against the day's confirmed adventures.

Phase F

Arrival, on-property & departure

Guests arrive on transfer day and are checked in; the on-property days run — meals, fishing, the run sheet and the displays — and at the end each folio is settled at checkout.

14

Arrivals & departures

Transfer day: some guests arrive by float plane, private jet or road pickup while others depart. A manager overview lays out who's coming on which flight; a mobile dock greeter checks each guest in, counts their bags, and calls them to the dock for the transfer to the lodge.

Admin · dock & front desk

    Business rules

  • A transfer day is arrivals and departures at once; guests come in by scheduled flight, private jet, or hotel/B&B pickup.
  • The manager overview shows who's coming grouped by flight/pickup, with the day's counts — arriving, departing, returning, groups.
  • The dock greeter (built for a phone) lists each guest with tap-to-call, a bag counter, and a done toggle — meet everyone, collect & count bags, then transfer to the lodge.
  • Returning guests are flagged with their prior-stay count, straight off the master record (Stage 1).

Maps to schema

Reads each guest's flight/arrival details from trip_profiles and the group roster; the returning-guest count comes from the person's history across trips. Bag counts and done-state are operational.

15

The check-in process

Check-in settles two decisions the group lead makes — who pays for each guest's add-ons, and how each guest's fish is handled — either in the portal beforehand or completed at the desk. This process map traces every step, its tool, and where it happens, including the required FedEx risk disclaimer.

Admin · front deskGuest · confirms in portal

    Business rules

  • Two lead decisions: who pays (per guest, per charge type) and fish handling — made in the portal, or completed at check-in if not done before arrival.
  • The assigned guest confirms in their own portal: payment responsibility, fish handling, and — for FedEx — a required risk disclaimer they must accept, which is logged to their record.
  • It then flows to checkout: every charge lands on the right folio (the Billing Report), and each guest's fish goes to the processor with their chosen handling.
  • Each step is tagged with its build status, so the dev team sees what's built versus what needs wiring.

Maps to schema

Ties together the payment routing on assignments (Stage 7), fish_processing and its splits, the guest-confirmation records (with the disclaimer acceptance stored on the person), and the checkout folio the Billing Report reads.

16

Breakfast & beverages

Each night, the lodge takes the next morning's breakfast and the day's beverage order — per guest. Breakfast is free choice from that day's menu; beverages roll onto the boat-stocking list by whichever boat the guest is on that day. It produces two outputs: a kitchen sheet and a boat-stocking list.

Admin · kitchen & dockGuest · can pre-set

    Business rules

  • Orders are captured per guest, per night, for the following morning.
  • Breakfast is free choice from that day's menu (mains + add-ons/mods).
  • Beverages are ordered by the 6-pack and roll onto the boat-stocking list for the boat that guest is on that day.
  • Two outputs come from the same order: a kitchen sheet (by guest) and a boat-stocking list (by boat).

Maps to schema

Each order is an assignment per guest per day, with the picks in details JSON. The menu and beverage catalogs are Breakfast and Beverage assets. Boat-stocking is derived by joining orders to the day's boat seating.

17

Fish processing

At the end of each fishing day, the group's catch is logged once. The engine yields filet weight per species (count × average weight × recovery %), totals the day, and splits it into however many take-home shares the group wants — one named guest per share. Each share's poundage lands on that guest's own record, so it rolls up per individual for the trip.

Admin · processing

    Business rules

  • Catch is logged per group, per fishing day, by species.
  • Filet yield = count × average weight × recovery %, summed to a day total in pounds of filet.
  • The day's filet is split into N take-home shares, each assigned to one named guest.
  • Each share's poundage attaches to that guest's record — the catch funnels to the individual, just like every other assignment.
  • Per guest: how the fish goes home (carry-on / ship), whether they keep collars & bellies, and who pays.

Maps to schema

fish_catch (trip, group, date, species, count, avg_weight, recovery) → fish_catch_split (share_index, person_id, lbs) → fish_payment (payer, method). Every share row references a person; no card number is ever stored, only a payment-method reference.

18

The daily run sheet

Everything above comes together here: the dock-and-spa run sheet for a single day, every assignment by individual guest. Boats list their captain, deckhand and seated guests; the spa lists each appointment by time; adventures list each guide's guests; and anyone not on the water is accounted for. This one sheet is why every stage insists on attaching to the person.

Admin · daily ops

    Business rules

  • The sheet is entirely by individual — boats name each seated guest under their crew; the spa names each guest by time; adventures name each guide's guests.
  • A guest booked on an adventure is pulled off the boat for that day (the activity-priority rule from Stage 7, made visible).
  • An evening massage keeps a guest on the water that day; a day-spa booking takes them off it.
  • Everyone present but not on a boat or activity is listed under "Enjoying the Island," grouped by party — nobody is unaccounted for.
  • The sheet pulls live from boat assignments and approvals, and prints for the dock.

Maps to schema

Pure read model: it joins the day's assignments (boats, activities, spa) with the trip roster from trip_profiles, applies the activity-priority rule, and groups the remainder. No new tables — it's the payoff of the individual-first design.

19

The guest displays — morning & evening

The same day, shown to guests on the lodge's screens. A morning board rotates through each boat with its crew and anglers and the day's activities; an evening board features tomorrow's breakfast and the day's activities and cocktails. Both are full-screen, auto-advancing, and read live from the very schedule the run sheet uses — nothing is entered twice.

Guest-facing · lobby & dock screens

    Business rules

  • The morning display — Boat & Activity Schedule — rotates a slide per boat (captain, deckhand, seated guests) and per activity, as a rolling full-screen slideshow.
  • The evening display features tomorrow's breakfast (the signature dish and the morning's choices), the day's featured activities, and cocktails.
  • Both pull live from the same data as the daily run sheet — boat assignments, approved activities, and the menus — so the wall screens are never out of date and nothing is re-typed.
  • Each is built for a wall-mounted TV: auto-advancing, full-screen, with a small Setup panel to choose what's featured and the slide timing.

Maps to schema

Read-only views over the day's assignments (boats, activities) joined to the Breakfast, Beverage and Activity assets and the team crew. No writes — the displays only present what the run sheet already resolves for the date.

20

Departure & billing

At checkout, every add-on a guest incurred — activities, spa, alcohol, fish processing — is itemized on their folio and routed to whoever the lead assigned to pay. The billing report totals it per guest, per group and a grand total, ready to settle.

Admin · checkout

    Business rules

  • Every activity, spa/massage and alcohol charge is itemized per guest — dated, described, with its amount.
  • Each charge routes to the assigned payer (Stage 7): a guest's massage can read "→ billed to the group lead," and it lands on that payer's folio instead.
  • Totals roll up per guest, per group, and a grand total to bill.
  • It's a draft folio — rates confirm against the catalog before billing, and state & city taxes and fees apply per lodge policy.

Maps to schema

Reads the checkout folio — charges on assignments routed to their assigned payer — plus fish-processing fees. Taxes and fees are applied at billing time; payment settles against a payment_method_id reference, never a stored card.

Phase G

Post-stay

A day after the guest checks out, the loop closes: a survey goes out, the answers become a score and a set of notes, and both attach back to the individual record — ready for the next visit.

21

The satisfaction survey

One day after checkout, each guest is automatically sent a pre-identified survey — short, on one standardized scale, grouped by department. If a rating is average or poor, it quietly asks how the lodge could do better. And if the guest is planning a return, it invites them to look at next year's calendar with a standing discount.

Guest · post-stay

    Business rules

  • Sent automatically one day after checkout, pre-identified to the guest (no "who are you?" step).
  • Ratings are standardized to one 4-point scale (Excellent / Good / Average / Poor), grouped by department.
  • Any Average or Poor rating reveals a "Tell us — how can we do better?" field, captured for service recovery.
  • Answering that they're planning a future stay reveals a rebook prompt to review next-year availability.
  • Business rule: a 10% discount is automatic for reservations made within 15 days of departure — and the survey lands inside that window.

Maps to schema

A survey response is another record type pointing at the guest's person (like an inquiry or a booking). Answers and write-ins are stored per question; the response feeds Stage 12's scoring.

22

Scoring & analysis

Every response becomes a number. Each rating maps to points, questions roll up into department scores, and the departments average into one guest satisfaction score from 0–100. Low answers flag the department for follow-up now; a monthly rollup goes to each department. Recommend and rebook are tracked separately as advocacy, not folded into the score.

Admin · reports

    Business rules

  • Each rating → points: Excellent 100 · Good 75 · Average 40 · Poor 0.
  • Questions roll up into departments — Service, Facilities, Culinary, Guiding, Spa — and the answered departments average into the 0–100 guest score.
  • Bands: 90–100 Exceptional · 75–89 Strong · 60–74 Watch · under 60 At-risk (auto-flags follow-up).
  • Any Average/Poor answer raises a service-recovery flag routed to that department.
  • Recommend and rebook are tracked separately as advocacy/retention, never inside the score.
  • Each department receives a monthly analysis of its own scores and comments.

Maps to schema

Scores are computed from the response and written to survey_scores, linked to the person and the trip. Department rollups and top-box percentages are derived; the latest and average score also cache onto the person for quick history.

23

It travels with the guest

The loop closes back to Stage 1. On the guest's staff-only profile, the score is published with a plain breakdown of how it was built — and, more importantly, their survey comments become carry-forward notes the lodge acts on in future years. A comment can catch what a score hides: a breakfast rated "excellent" whose note mentions a 30-minute wait becomes a flag for next season.

Admin · staff-only profile

    Business rules

  • The score is published on the guest's profile for staff eyes only — never shown to the guest.
  • The profile shows how the score was built (answer → points → department → score), so it's transparent to management.
  • Survey comments become carry-forward notes, tagged Fix or Delight, routed to a department and dated to the year.
  • Notes catch what the number hides — an "Excellent" breakfast whose comment flags a long wait still raises a Fix note.
  • Each note carries Carry-to-next-stay / Mark-addressed, and a year-over-year comment history shows the whole relationship.

Maps to schema

The score reads from survey_scores; the carry-forward notes are person-linked records with a tag, department, source year and status. Because they hang off the person, they resurface automatically the next time that guest books — the accumulation promised in Stage 1.

Appendix

API contract

A proposed contract for the endpoints each screen needs and the shapes they exchange — for Stella's team to ratify against the locked v4 schema. Grouped to match the stages above; representative payloads shown, not every field.

Base/api/v1 · JSON in and out. AuthStaff calls send a Bearer session (RBAC); /portal/* uses the guest's magic-link session. Auth is Stella's — this contract assumes it. IDsEvery entity has a ULID id. Servers stamp created_by / updated_by + timestamps. DeletesSoft-delete only (active:false) — no endpoint hard-deletes. Lists{ data:[…], meta:{ total, page, per_page } }. Errors: { error:{ code, message, fields? } }. MoneyNo card number is ever sent or stored — only a payment_method_id reference.
1 · People & matchingStage 01
POST
/intake/:channel
Stage 01 · channel = inquiry|lead|reservation|guest-list. Runs the matcher, returns the resolved person and the tier decision.
GET
/persons/:id
The master record — emails, phones, aliases, every group/trip/role, and cached rollups.
GET
/persons?q=&page=
Search by canonical_name / email / phone.
GET
/merge-review
The Tier-3 queue awaiting a human decision.
POST
/merges
{ survivor_id, loser_id } — combine two people; snapshotted and reversible.
POST
/merges/:id/undo
Reverse the most recent not-yet-undone merge on a survivor.

  "created": false }

2 · Assets & catalogStage 02
GET
/assets?type=
Stage 02 · type = room|activity|boat|guide|breakfast|beverage…. Returns the properties JSON per asset.
POST
/assets
Create an asset of a type with its properties bag.
PATCH
/assets/:id
Edit an asset; properties is validated by its field-definitions.
POST
/asset-links
{ from_asset_id, to_asset_id, capability } — link a guide to an activity, a captain/deckhand to a boat.
GET
/field-definitions?target=
target = asset|trip_profile|assignment|person. The meta-schema that drives every form — no migration to add a field.
